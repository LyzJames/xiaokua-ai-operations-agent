# 架构与研究取舍

## 研究问题

如何让一个办公软件中的数字员工跨系统执行任务，同时让每次写入具有清楚的授权、可检查的依据和可恢复的状态？此原型研究显式业务流程，不把模型生成的自然语言直接当作平台操作权限。

## 0.2 的状态模型

- `events` 保存最小化事件及去重身份。
- `tasks` 保存组织、申请人、任务参数、状态和结果。
- `actions` 保存操作前快照、拟写入数据、独立审批人、有效期及平台结果。
- `jobs` 保存持久作业、租约、心跳和错误；worker 重启重新领取安全恢复的作业。
- `resources` 保存订单/商品快照与导入客服记录；`knowledge` 保存带证据的已确认知识。
- `audits` 形成追加式哈希链，组织头在事务中锁定；数据库触发器禁止普通更新和删除。

业务写入状态大致为 `pending → approved → executing → executed`。拒绝、失效、过期、失败和结果未知各有独立状态。先持久化执行意图再请求平台；外部状态未知时不能把重启当成重发许可。

## 编排与多角色

主分析图使用 LangGraph：订单分析、库存分析与客服知识角色并行完成只读分析，随后汇总。每个报告包含依据和模式；没有相应平台数据时明确说明缺失，不编造退货率、制造批次或广告表现。

0.2 的持久执行依靠 SQL 任务队列，不宣称分析图本身启用了持久 checkpoint。历史 0.1 模拟模块 `backend/engine.py` 保留独立 LangGraph checkpoint 实验，两者不能混为一条平台写入链路。

当前范围没有加入 CrewAI 和 ContextDB：显式角色函数与关系库足以支持这个可审查流程，减少研究者需要配置的服务。后续可以抽象 role executor 与 knowledge store，但不能让框架替换审批和幂等约束。

## 记忆如何成为技能

导入去除个人信息的客服记录，以市场和主题分组。至少 5 条同类记录才生成草稿，保留样本证据，默认未启用。运营人员核对产品规格和退货政策后启用，再由市场/主题检索供分析复用。导出为 Markdown 便于审查与版本管理。

草稿只总结咨询关注点，不自动承诺能效等级或本地退货资格。当前是规则主题识别和带证据检索，没有向量语义记忆或通用自主技能代码执行。

## 离线演示为何可信、又能证明什么

`backend.demo` 复用真实 API、RBAC、CSRF、事件处理、队列、审批、执行与审计；只通过实例依赖注入替换平台客户端、消息发送与模型模式。`DemoShop` 用 JSON 持久化合成店铺，模拟台用登录成员身份构造事件。

验收脚本禁止 HTTPTransport 出站请求，因此可以证明这些业务逻辑不依赖实际凭据完成闭环。它不能证明 Shopify 或飞书当前授权有效，不能替代网络故障、平台时序和商店审核的真实验收。

## 尚未覆盖的研究方向

Amazon、Meta 与真实采购支付尚未实现平台适配；UI 中明确为后续方向。没有真实 AI 钱包、供应商采购、全自动投放或无需审批的退款。多租户的大规模运行、外部审计锚、长连接调度、通用语义记忆与平台版本迁移可作为后续课题。
