### 完整测试中发现并修正的问题

| 问题 | 修正及复验 |
| --- | --- |
| 后台有库存，前台却显示售罄 | 初始测试库存位于不能配送的地点。初始化脚本改为检查主配送地点，测试商品配置单独的欧洲配送范围及零运费；三次前台结账都实际成功，库存按预期扣减。 |
| 合成 `.invalid` 邮箱被结账的域名校验拒绝 | 买家结账使用 IANA 保留的 `example.com` 示例域；本机应用的合成登录账号仍可使用 `.invalid`。 |
| 分析指定订单时可能带入全店快照，或多笔订单中一笔缺明细被其他订单掩盖 | 从命令提取明确订单编号，在模型调用前限定订单和相关商品；逐笔核对明细与分页状态，未知编号或不完整明细拒绝分析。真实三角色分析、上下文隔离和缺失/截断明细的失败路径均通过。 |
| 库存角色缺少实际数量和本单需求 | 增加已同步的汇总可用数量、订单需求及可配送库存的限制说明，保持输入与引用预算一致；重新发送真实案例分析并导出报告通过。 |
| 验收工具的 HTTP 客户端被重复进入 | 修正客户端生命周期，补充认证导出与关闭验证；真实模型报告、技能包和审计导出均通过。 |
| 已有分类报告文件时，重复回归命令未识别报告参数 | 将 pytest 报告钩子移至仓库根目录，保证参数预解析时能够加载；再次运行同一报告路径的完整数据库回归通过。 |

平台准备与业务修正没有关闭测试保护，也没有购买物流标签、开启真实采购付款或改用真实卡片。

### 并行、结构和恢复的自动化证据

三个角色通过并发屏障验证原生并行，各自只接收订单统计、库存统计或匹配知识。Pydantic 拒绝未知字段、错误类型、超长结果和伪造引用；越权退款字段不能转成操作方案。截断输出、鉴权错误和无效 JSON 明确回退，只有超时及短暂服务故障在预算内重试。

角色结果保存到 `analysis_steps`。测试让库存角色中断，关闭数据库连接后重建服务，再次运行同一任务，验证订单和知识角色复用成功结果，仅重新分析缺失部分。库存快照或技能启用状态改变，会使相应角色的输入指纹失效。PostgreSQL 也验证步骤保存、重开与复用。

这是应用层 SQL 步骤日志，不是 LangGraph checkpointer。模型已经响应但结果尚未保存时崩溃，恢复可能重复请求；引用属于允许范围也不等于自然语言结论已被证明。研究取舍见 [技术调研](TECH_REVIEW.md)。
